🔒 Feature Privacy

⚙️ How FraudShield Works — End to End
Every transaction — whether entered manually, through the Smart Form, CSV upload, or Live Feed — follows the exact same inference pipeline. Here is every step from input to final decision.
1
User Input
Three input paths all produce the same 30-number feature array:
Smart Form — user fills ₹ amount, merchant, location, time, card type → fraud score computed → PCA features interpolated (see Section below)
Raw CSV — user pastes 30 comma-separated values directly
CSV Upload — batch file, each row becomes one prediction
2
POST /predict — Flask API receives the request
The JavaScript frontend sends a JSON body to http://127.0.0.1:5000/predict:
{ "features": [v1, v2, ..., v28, amount, time], "model": "xgboost" }
Flask's _resolve_model() reads the "model" key and selects the correct .pkl file — XGBoost, Random Forest, or Logistic Regression.
3
predict_transaction() — post.py
Logistic Regression only: features are passed through lr_scaler.pkl (StandardScaler fitted on training data) before inference. Tree models receive raw features.

Model inference: model.predict_proba(features)[0][1] returns a float in [0,1] — the probability that this transaction belongs to class 1 (Fraud).

Decision threshold: XGBoost and RF use 0.5. Logistic Regression uses a tuned threshold stored as model.best_threshold_ (found via precision-recall curve during training) because LR's raw probabilities are miscalibrated after SMOTE.
4
generate_reasons() — post.py
After the model predicts, generate_reasons() analyses the raw feature values against known fraud/legitimate distribution means from published ULB dataset research. It checks:
V3 < −5.0 → fraud signal
V14 < −6.0 → top signal
V17 < −5.0 → fraud signal
V4 > +3.0 → fraud signal
Amount > 1000 → elevated
V12 < −4.0 → fraud signal
Returns verdict_reason (one sentence), factors (list of specific findings), feature_flags (triggered feature names), and a full summary paragraph.
5
UI displays result + reasons
The frontend receives the JSON response and simultaneously updates:
— Result card: Fraud/Not Fraud label, probability bar, risk level, confidence, "Why This Decision" reason box
— History table: new row with Why? column showing reason snippet + feature flag pills
— Dashboard charts: fraud rate line, distribution bar, model usage bar all update
— Notification bell: if Fraud → bell shakes, badge increments, alert pushed to panel with full reason detail
— Live Feed: transaction card shows merchant, amount, reason snippet, feature flags
HOW THE 3 DISPLAY VALUES ARE CALCULATED
Risk Probability %
model.predict_proba()[0][1] × 100
Direct output of the model. The probability that this transaction belongs to class 1 (Fraud). No post-processing — raw model confidence.
Risk Level
prob > 0.7 → High · > 0.4 → Medium · else Low
Simple threshold bucketing applied to the raw probability. These thresholds are hardcoded — not learned from data. Used for quick visual triage.
Confidence %
(1 − |prob − 0.5| × 2) × 100
Measures how far the probability is from the 0.5 decision boundary. Probability = 0.99 → confidence 2% (extreme but uncertain). Probability = 0.01 → confidence 2%. Probability = 0.5 → confidence 100% (perfectly on the fence).
🔢 How V1–V28 Are Calculated — From Real Transaction to Feature Vector
The 30 numbers you enter into FraudShield (V1–V28 + Amount + Time) come from a process called Principal Component Analysis (PCA). This section explains exactly what PCA does and how a bank would produce these numbers from a real transaction.
STEP 1 — WHAT A REAL TRANSACTION CONTAINS
When you swipe or tap a card, the bank's system captures dozens of data points about that transaction:
TRANSACTION
Amount · Currency · Timestamp · MCC code (merchant category) · Terminal ID · Transaction type (POS/online/ATM)
CARDHOLDER
Card age · Credit limit · Average spend · Number of txns today · Distance from home city · Device fingerprint
CONTEXT
Time of day · Day of week · Country of merchant · IP geolocation · Velocity (5-min, 1-hr, 24-hr txn count)
In the ULB dataset this might be 30–50+ original features per transaction — but the bank cannot release them publicly because they would identify cardholders. So they applied PCA.
STEP 2 — WHAT PCA DOES TO THOSE FEATURES
PCA is a mathematical transformation. It takes the original N features and produces N new features (called principal components). Each component is a weighted combination of all original features:
V1 = 0.31×Amount − 0.12×MCC + 0.08×CardAge + 0.44×TimeOfDay − 0.19×Velocity + ...
V2 = −0.22×Amount + 0.35×MCC − 0.41×CardAge + 0.09×TimeOfDay + 0.28×Velocity + ...
... (weights are learned from the full training dataset)
✓
Privacy: Since each V value mixes all original features together, you cannot reverse-engineer V3 = −7.1 back to "merchant was XYZ in Delhi" — the original meaning is mathematically hidden.
✓
Variance ordering: V1 captures the most variance (most information) in the dataset, V2 the second most, and so on. V28 captures the least. This is why V3 and V14 are such strong fraud indicators — they capture patterns that vary dramatically between fraud and legitimate transactions.
✓
Standardised output: After PCA, each component is StandardScaled to zero mean and unit variance. That is why V values are always roughly between −5 and +5 for legitimate transactions — they are Z-scores in the PCA space.
STEP 3 — HOW FRAUDSHIELD'S SMART FORM APPROXIMATES V1–V28
The actual PCA weights from the ULB bank are not public — they never released the transformation matrix. So when you use the Smart Form (entering ₹ amount, merchant, time of day etc.), FraudShield uses a statistical approximation based on published research about the dataset's fraud/legitimate feature distributions:
1. Compute Fraud Score (0–1) from your inputs: International location +0.25 · Late night +0.20 · Amount > 10× daily avg +0.35 · New card +0.10 · 10+ txns today +0.20 · NEFT/wire transfer +0.10 · ATM/banking merchant +0.15
2. Interpolate between distributions using the fraud score as weight:
V3 = lerp(0, −7.03, fraudScore) + noise
fraudScore=0 (completely legit) → V3≈0 · fraudScore=1 (completely fraudulent) → V3≈−7.0
3. Add realistic noise so the generated values look like real PCA output, not perfectly uniform numbers. Each feature gets Gaussian noise proportional to the known standard deviation in the dataset.
⚠ Important: This is a statistical approximation — not the real PCA transform. In a real bank deployment, the bank's own system would compute the actual V1–V28 values using their private transformation matrix and feed them directly to the /predict API. The Smart Form exists to make the demo usable by people who don't have access to raw PCA-transformed data.

Stage 1 — User Input
The user enters transaction details through one of three modes: Smart Form (human-readable — amount in ₹, merchant type, card type, time, location, etc.), Raw CSV String (the 30 PCA values directly), or Individual Fields (each V1–V28, Amount, Time field separately). The Smart Form is the most user-friendly — no knowledge of PCA required.
Stage 2 — Feature Conversion (Smart Form only)
The Smart Form inputs are converted into a 30-dimensional feature vector using a statistical mapping. Each dropdown selection contributes to a fraud risk score (0–1) based on known fraud patterns from the ULB dataset. This score then interpolates between the legitimate feature distribution (all V values near 0) and the fraud feature distribution (V3≈−7, V14≈−9, etc.). The result is a realistic approximation of what the PCA feature vector would look like for that type of transaction.
Stage 3 — API Call to Flask Backend
The 30-feature array is sent as a JSON POST request to http://127.0.0.1:5000/predict. The request body contains the features array and the selected model name ("xgboost", "rf", or "logistic"). Flask receives it, validates the 30 features, and routes to the correct model.
Stage 4 — Model Inference
The selected model runs predict_proba(features) and returns the probability of fraud (class 1). For Logistic Regression, the features are first scaled using the saved lr_scaler.pkl, and a precision-recall tuned threshold (not the default 0.5) is used for the final decision. XGBoost and Random Forest use the raw features and standard 0.5 threshold.
Stage 5 — Reason Generation
The generate_reasons() function in post.py analyses the actual feature values against known fraud/legitimate distribution means. It checks V3, V4, V9, V10, V11, V12, V14, V17, and Amount against thresholds derived from published ULB dataset research, counts how many fraud signals are present, and produces: a one-line verdict, a list of 3–5 specific factor explanations, the triggered feature names, and a full summary paragraph.
Stage 6 — Display & Alert
The response is displayed in the result card with the prediction label (Fraud / Not Fraud), risk probability bar, risk level (High/Medium/Low), confidence %, and the full "Why This Decision" explanation box. If fraud is detected, the notification bell animates, a fraud alert card is pushed to the panel with a reason preview, and the full detail modal (accessible by clicking) shows all 30 features, key fraud signal bars, and the complete explanation.
🧮 What Are V1–V28, Amount & Time? How Are They Calculated?
This is the most common question. The answer requires understanding what the bank originally collected, and what they chose to share publicly.
WHAT THE BANK ACTUALLY COLLECTED (ORIGINAL FEATURES)
📍 Transaction location & merchant category
💳 Card type, age & spending history
⏰ Time of day & velocity of recent transactions
📱 Device fingerprint & IP geolocation
🌍 Country of transaction vs. card country
💰 Average spend pattern & anomaly score
These are the real transaction features the bank used — but they are confidential. Publishing them would allow fraudsters to engineer transactions to evade detection, and would violate cardholder privacy.
HOW V1–V28 ARE CALCULATED (PCA TRANSFORMATION)
The bank applied Principal Component Analysis (PCA) to all the original features before publishing the dataset. PCA is a mathematical transformation that:
1 Takes all original features (location, card type, velocity, device, etc.) and finds the directions of maximum variance in the data — essentially the most "informative" combinations of the original features.
2 Projects every transaction onto 28 of these "principal component" directions. Each resulting number (V1, V2… V28) is a weighted combination of all the original features — not a single original feature.
3 Anonymises the data — you cannot reverse the PCA to recover the original feature values without the original PCA matrix (which the bank keeps private). V14 = −9.2 tells you nothing about what specific transaction detail caused it.
4 Preserves fraud detection power — even though the features are anonymised, the ML models can still find patterns because fraud transactions cluster in specific regions of this transformed space.
CONCEPTUAL FORMULA
V1 = w₁₁×(merchant_cat) + w₁₂×(location) + w₁₃×(velocity) + w₁₄×(card_age) + …
V2 = w₂₁×(merchant_cat) + w₂₂×(location) + w₂₃×(velocity) + w₂₄×(card_age) + …
⋮
V28 = w₂₈₁×(merchant_cat) + w₂₈₂×(location) + … + w₂₈ₙ×(feature_n)
where w values are the PCA eigenvectors — kept secret by the bank
AMOUNT AND TIME — THE ONLY ORIGINAL FEATURES
Amount
The actual transaction value in Euros (the dataset is from European cardholders). It is kept in its original scale. In FraudShield's Smart Form, this maps to Indian Rupees (₹) for local context, and the entered amount is used directly as the Amount feature. Fraud transactions often have unusually high amounts for the cardholder's normal pattern.
Time
NOT a clock time. It is the number of seconds elapsed since the first transaction in the dataset. The dataset spans 2 days (172,792 seconds). A Time value of 86,400 means this transaction happened ~1 day after the dataset began. It helps capture time-of-day fraud patterns — late-night transactions correlate with higher fraud rates.
HOW FRAUDSHIELD CONVERTS YOUR ₹ INPUTS TO V1–V28
Since the real PCA matrix is private, FraudShield's Smart Form uses a statistical approximation based on published ULB dataset research. Here's exactly what happens when you fill the Smart Form:
Step 1 — Compute fraud risk score (0 to 1): Each form field contributes to a risk score based on known fraud patterns. Late night → +0.20, International location → +0.25, Amount 10× above daily average → +0.35, New card → +0.10, 10+ transactions today → +0.20, NEFT/Wire transfer → +0.10. These weights come from the fraud signal distributions in the ULB paper. The score is clamped to [0, 1].
Step 2 — Interpolate between distributions: For each V feature, we know the legitimate mean (~0) and the fraud mean (e.g., V3 fraud mean = −7.0). Each feature value is calculated as: V_value = legitimate_mean + fraud_score × (fraud_mean − legitimate_mean) + noise. A fraud score of 0 produces all-zero features (clean). A fraud score of 1 produces the full fraud pattern (V3≈−7, V14≈−9, etc.). Intermediate scores blend proportionally.
Step 3 — Amount and Time: Amount is taken directly from your ₹ input (the model was trained on Euros, but since all features are normalised inside the model, the currency scale does not significantly affect results for demo purposes). Time is randomised in the valid dataset range (0–172,792 seconds).
Step 4 — Send to model: The resulting 30 values [V1…V28, Amount, Time] are sent to the Flask API exactly as if you had typed them in the Raw CSV tab. The model has no knowledge of how they were generated — it just sees 30 numbers and makes its decision.
⚠ Important note: This is a statistical approximation, not the real PCA transform. In a real bank deployment, the system would receive the actual PCA-transformed values directly from the transaction processing system — no conversion needed. The Smart Form demonstrates the concept for educational and demo purposes.
